## 1. Принципы консистентности бронирования

- **Только одно активное бронирование на таймслот:**
  - обеспечивается частичным уникальным индексом в БД `uq_bookings_timeslot_active`
  - активные статусы: `PENDING_PAYMENTS` и `PAID`

- **Выбор слота при конкуренции:**
  - в процессе бронирования строка таймслота блокируется через `SELECT ... FOR UPDATE`
  - параллельные запросы не могут создать два активных бронирования для одного слота

- **Допустимый переход состояния оплаты:**
  - бронирование может перейти в `PAID` только из `PENDING_PAYMENTS`
  - реализовано через условный запрос:
    ```sql
    UPDATE bookings
    SET status = 'PAID'
    WHERE status = 'PENDING_PAYMENTS'
      AND expires_at > now();
    ```

- **Правило отмены:**
  - отменить можно только бронирование в статусе `PENDING_PAYMENTS`
  - уже отменённые / оплаченные / истёкшие бронирования отклоняются

## 2. Идемпотентное создание бронирования

- Клиент может передать заголовок `Idempotency-Key` (UUID) для:
  - `POST /bookings`
  - `POST /bookings/flexible`

- **Фингерпринт запроса формируется из:**
  - имени операции
  - id пользователя
  - тела запроса

- **Фингерпринт и ответ сохраняются в Redis:**
  - ключ: `idempotency:booking:{user_id}:{uuid}`

- **Первый запрос:**
  - резервирует ключ через атомарный `SET NX` с TTL
  - выполняет создание бронирования
  - сохраняет готовый ответ в Redis

- **Повторный запрос с тем же ключом:**
  - тот же фингерпринт → возвращается закэшированный ответ (идемпотентность)
  - другой фингерпринт → `409 Conflict`
  - если запрос всё ещё выполняется → `409 Conflict`
